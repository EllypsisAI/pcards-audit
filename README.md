# OSU P-card audit — Analytics Mindset case

Internal-control and forensic testing of Oklahoma State University purchasing-card (P-card)
transactions for calendar year 2014, plus a two-tab website auditors can use to question the
data themselves.

Course: AI in Accounting and Business (B150316101), SDU, autumn 2026.

**Live site:** _added on deploy_

## What is here

| Part | Scope | Where |
|---|---|---|

| III | 8 forensic tests — 4 specified, 4 student-defined | `sql/qry_T3_QuestionN.sql` → `results/qry_T3_QuestionN.csv` → [`docs/part3-results.md`](docs/part3-results.md) |

## How the work was done

Every number in the write-ups comes from a query in `sql/` and is regenerated by one command,
so nothing quoted is typed in by hand. The method throughout:

1. **Profile the data before testing it.** The quirks below were found first, and each one
   would otherwise have produced a wrong result silently.
2. **Run the test as specified, then read the flagged rows.** Several first versions were
   wrong in ways only the rows revealed — `%ATM%` matched *treATMent*; a merchant-type test
   for donations returned $489k that turned out to be fire-code standards and journal fees.
   Each correction is recorded in the query's header comment.
3. **Add a second dimension** — amount, frequency or vendor — before calling anything a
   finding. Merchant category describes the merchant, not the purchase.
4. **Size the alternatives.** The student-defined tests were chosen from a longer list; the
   rejected candidates and their numbers are kept in `sql/considered/` rather than discarded.
5. **State what the data cannot settle.** Every conclusion says what evidence would move the
   flag either way. A flagged transaction is a risk indicator, not a violation.

The analysis, code and write-ups were produced with an AI coding assistant (Claude Code),
directed and reviewed by the author: test selection, the choice between candidate tests and
the conclusions were decided in discussion, then verified against the data.

## Running it

The course-provided database goes in a sibling folder, `../pcards/pcards.db`.

```bash
python3 run.py              # every query in sql/, results to results/
python3 run.py Question9    # one query
python3 build_db.py         # rebuild data/pcards.db.gz for the website
```

Website, locally:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env        # add a Gemini API key; the dashboard tab works without one
.venv/bin/streamlit run app.py
```

Deployed on Streamlit Community Cloud. The API key is entered in the app's **Secrets**
settings there and is never in this repository; `.env` and `.streamlit/secrets.toml` are
git-ignored.

## The data

489,178 transactions, all Oklahoma State University (agency 1000), 2010–2014 — despite the
case describing a state-wide extract. 116,031 fall in 2014: $33.5m across 2,021 cardholders.

- `Year` matches the year of `TransactionDate` on all 489,178 rows, so `Year = 2014` is an exact
  calendar-year filter.
- `TransactionDate` is text, `M/D/YYYY 0:00:00`, and **does not sort**. Queries parse it; the
  website's database adds ISO `TxnDate` / `PostDate` columns so model-written SQL cannot get
  date order wrong.
- Cardholders are pseudonymised (`Employee 51914657`), with no department, card limit or
  approver — so several tests can rank risk but not settle it.
- The vendor field is not a vendor identifier: one supplier appears under 283 spellings.
- About two thirds of descriptions say only `GENERAL PURCHASE`.

## The website (Part IV)

**Ask the database.** The auditor picks a year and types a question. Gemini returns one SQL
query, a plain-English explanation and a list of caveats; the app checks and runs the query and
shows the answer, the exact SQL, the caveats, response time and token use, with a CSV download.
Model-written SQL is treated as untrusted: the database is opened read-only, a SQLite
authorizer refuses anything but reading the `pcards` table (no writes, `ATTACH`, `PRAGMA` or
schema tables), and a query running longer than 15 seconds is stopped.

**Prohibited purchases.** Year selector, written instructions, and two separate searches —
Description and Vendor — over fixed, parameterised SQL with no language model. Keyword
matching is whole-word by default (the `ATM` lesson from Control 12), with a toggle for
fragments. Results carry the fields needed to request a receipt, a summary of who to follow up
first, and a CSV download. The page states, for the selected year, how much of the description
field is uninformative, so an empty description search is not mistaken for a clean result.
